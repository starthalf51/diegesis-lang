# File format — front matter + language blocks + prose body

> One file = one module = `.dieg.md`. Any Markdown viewer can open it as is.
> Front matter is **syntactic sugar** for the language. It compiles to the same IR as language blocks, and writing the same information in both places is a compile error. → [language](language.md)

## Structure

````markdown
---                                  ← ① front matter: static properties of this file itself
scene: "1.3"
location: heath
when: after 1.2 by 0d..1d
characters: [witches, macbeth, banquo]
pov: macbeth
mode: authored
---

```sl                                ← ② language block: dynamic elements (several allowed, joined in order)
beat prophecy:
  witch1 hails macbeth: holds(thane_of_glamis, macbeth)
  ...
exit witches
enter ross, angus
```

Upon the blasted heath the three shapes rose out of the fog...   ← ③ prose body
````

| Layer | Holds | Does not hold |
|---|---|---|
| ① Front matter | Per-file properties: module, imports, scene ID, place, viewpoint constraints, characters present **for the whole scene**, characters only mentioned, the viewpoint character, render directives, work status, prose mode. For a declaration file, also the entity lists | Time relations that refer to other events: speech, perception, belief, deception, causation, mid-scene entrances and exits, role-holding spans |
| ② Language block | Everything above that does not go in front matter | — |
| ③ Prose | Sentences written by the author or generated by the renderer | Meaning. Prose is not checked |

There is one rule for the boundary: **a property of this file itself that does not refer to another event may go in front matter.** Time relations go in language blocks. As an exception, a scene's own `when` is allowed in front matter.

- Front matter must open with `---` on line 1 and closes at the next `---` line. A language block runs from ```` ```sl ```` at column 0 to ```` ``` ````.
- If the extension is `.dieg`, the whole file is language source (no front matter, no prose).

### Minimal file

A language block alone, without front matter, is also a file. In that case the first statement is `module`. This repository's doc-example test (`TestDocsExamplesCompile`, for blocks marked `<!-- check -->`) compiles a block that starts with `module` as it is, and otherwise prepends `module: docs.ex` front matter and compiles it as a single `.dieg.md` file.

<!-- check -->
```sl
module demo.minimal

work demo
  unit day
character anna "Anna" major
place hall

scene 1 at hall
  when after start
  enter anna
  anna says: "Hello." src 1.1
  exit all
```

## Sugar → language mapping (part of the specification)

Every key has an equivalent language statement defined for it. Right after parsing, the compiler replaces front matter with these statements, and later stages do not tell the two apart.

| Front matter | Equivalent language statement |
|---|---|
| `module: macbeth.act1` | `module macbeth.act1` |
| `import: [macbeth.cast]` | `import macbeth.cast` |
| `scene: "1.3"` + `location: heath` | `scene 1.3 at heath` (the whole block becomes the body of this scene) |
| `when: after 1.2 by 0d..1d` (a list is allowed) | `when after 1.2 by 0d..1d` |
| `date: 1805-07-?` / `time: dawn` | `when at 1805-07-? dawn` |
| `characters: [a, b]` | `enter a, b` as the scene's first line and `exit all` at the end |
| `mentions: [cawdor]` | `mention cawdor` (not attendance) |
| `pov: macbeth` | `pov macbeth` in the `render` block |
| `render: {pace: slow, tension: 0.8}` | the same keys in the `render` block |
| `thread: scotland` | `scene … in scotland` |
| `discourse: after 1.1` | `discourse after 1.1` |
| `characters:` map (declaration file) `macbeth: {name: Macbeth, tier: major}` | `character macbeth "Macbeth" major` |
| `places:` / `things:` / `factions:` / `facts:` / `groups:` maps | the corresponding declarations |
| `status`, `mode`, `rendered` | Metadata. They produce no statements |

A generated statement's position is that line of the front matter. This is why error locations point at lines of the original file.

### The rule that keeps each fact in one place

- **Writing the same fact in two places is an error (`dup-decl`).** Re-`enter`ing in the block a character already listed in `characters`, or having both a `scene` key and a `scene …` header line in the block, is an error.
- So a character who arrives mid-scene is written **only in the block**. `characters` means "characters present from start to end". `characters: []` means "nobody".
- A value that merges the two layers, such as the full attendance list, is **computed output**. It is not written by hand.

### YAML pitfalls

- YAML reads `scene: 1.3` as a float, and `1.10` becomes `1.1`. `no` becomes false (the Norway problem).
- So the compiler reads YAML **as nodes**, without type inference. Every scalar is taken as its original string, then interpreted directly with the types in the mapping table above. The result is the same even if the user forgets the quotes.
- Anchors, aliases and merge keys (`&`, `*`, `<<`) are forbidden (`yaml-anchor`), because they make information look as if it lives in two places. An unknown key is an `unknown-key` error.
- Values must be a single line (no block scalars or multi-line scalars).

## The two modes of the prose body

| | `mode: authored` (written by the author) | `mode: rendered` (generated by the renderer) |
|---|---|---|
| Owner of the body | The author | The renderer |
| What the compiler does to the body | **Leaves it alone.** Checks structure only | Same |
| Default | This mode, if there is a body | — |

- **Beat anchor** `<!-- beat:prophecy -->` (optional): an HTML comment invisible in previews, which must be a whole line by itself. It ties a position in the prose to a beat.
- **Blocks may be interleaved with prose.** Place ```` ```sl ```` blocks between paragraphs and they are joined in order.
- The checks for stale rendered prose (`stale-prose`) and for hand-edited traces (`rendered-edited`), and `verify-prose`, which re-extracts structure from prose and diffs it, exist only in the design and are not implemented. Today, staleness of rendered prose is decided by `dieg revise`, which compares a scene's render-request hash and world-state digest hash → [rendering](rendering.md)

## Directory convention

```
corpus/macbeth/
  cast.dieg.md          declarations only (front matter maps; roles and facts in blocks)
  act1/
    1.2.dieg.md  1.3.dieg.md  1.5.dieg.md  offstage.dieg.md
  texts/              public-domain source texts (targets of src line references)
  expect.yaml         acceptance criteria (dieg test)
```

One scene per file is the default. When putting several short scenes in one file, do not use front matter; write `scene` inside the block.

## Compatibility with existing tools (design-stage survey)

Story Skills (`danjdewhurst/story-skills`, MIT) is a bundle of novel-writing skills that stores chapters, scenes, characters, foreshadowing and knowledge state as Markdown with YAML front matter. Keys with the same concept have the same names (`location`, `characters`, `mentions`, `pov`, `date`, `time`, `status`). So its scene front matter reads as front matter here almost unchanged.

- Import is possible. Only what it lacks (speech, deception, relative time, beat positions) is empty.
- Export is a projection made from the IR. Deception, time constraints and the reader schedule are lost.
- Two-way sync is not done. It would put information in two places.
- `dieg import story-skills` / `dieg export story-skills` exist only in the design and are not implemented.
